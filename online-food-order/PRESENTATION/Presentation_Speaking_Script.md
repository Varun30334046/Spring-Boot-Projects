## Slide 2: Project Overview & Problem Statement
**Slide Title**: Project Overview & Objectives  

### Script to Speak:
"Modern food delivery platforms like Swiggy, Zomato, and Uber Eats rely heavily on backend web services. When a customer browses food or places an order on a mobile app, that mobile app communicates with a backend server using REST APIs.

The objective of our project is to develop a lightweight, robust backend service that handles the complete life cycle of an online food order:
- Allowing customers to place new food orders.
- Viewing all orders.
- Searching for specific orders by ID.
- Updating orders completely or partially.
- Canceling or deleting orders.

For this project, we intentionally stored data temporarily in memory using Java's built-in `ArrayList`, without using an external database like MySQL or MongoDB, so that our primary focus remains on mastering Spring Boot architecture, RESTful standards, and API validation."

## Slide 4: Layered Architecture & Project Structure
**Slide Title**: Layered Architecture & Separation of Concerns  

### Script to Speak:
"To keep the codebase maintainable and clean, we strictly followed a **Layered Architecture**. We divided the application into four distinct packages under `com.example.onlinefoodorder`:

1. **First, the Model Layer**: Contains `Order.java`, which defines our entity structure and validation annotations.
2. **Second, the Controller Layer**: Contains `OrderController.java`. It acts as the front door of our application, receiving HTTP requests and mapping endpoints.
3. **Third, the Service Layer**: Contains `OrderService.java`. It holds all business rules, auto-generates order IDs, and manages the in-memory `ArrayList`.
4. **Fourth, the Exception Layer**: Contains `GlobalExceptionHandler.java` and `ErrorResponse.java`. It centralizes error handling across the entire application.

By separating concerns this way, our Controller never touches the data collection directly, making the system modular and easy to test."

## Slide 5: The Model & Validation Rules
**Slide Title**: Data Model & Server-Side Validation  

### Script to Speak:
"Our data model is the `Order` class. It contains five essential fields:
- `orderId`: A Long that is automatically generated by the service.
- `customerName`: The customer's name.
- `foodItem`: The name of the dish ordered.
- `quantity`: The number of portions.
- `price`: The cost of the food item.

To guarantee that invalid data is rejected before processing, we implemented strict Jakarta validation annotations:
- `customerName` has `@NotBlank`, ensuring it cannot be empty or just spaces.
- `foodItem` also has `@NotBlank`.
- `quantity` has `@NotNull` and `@Min(1)`, ensuring an order must be for at least one item.
- `price` has `@NotNull` and `@Positive`, preventing negative or zero prices.

These validation rules protect our API and automatically reject bad requests with an HTTP 400 Bad Request status."

## Slide 6: REST API Operations (CRUD)
**Slide Title**: Six Core REST API Endpoints  

### Script to Speak:
"Our application implements all six essential REST API operations:

1. **GET `/api/orders`**: Retrieves all food orders currently stored in memory. Returns HTTP `200 OK`.
2. **GET `/api/orders/{id}`**: Searches for a specific order. If found, returns `200 OK`. If not, throws our custom `OrderNotFoundException` which returns `404 Not Found`.
3. **POST `/api/orders`**: Adds a new order with auto-generated ID. Returns HTTP `201 Created`.
4. **PUT `/api/orders/{id}`**: Replaces all editable fields of an existing order. Returns `200 OK`.
5. **DELETE `/api/orders/{id}`**: Deletes the specified order from memory. Returns `200 OK` with a success message.
6. **PATCH `/api/orders/{id}`**: Performs a partial update. For example, if a customer only wants to change the quantity from 2 to 5 without altering their name or dish, PATCH updates only the quantity and leaves other fields untouched. Crucially, we also validate the final merged order before saving."

## Slide 7: Centralized Exception Handling
**Slide Title**: Global Exception Handling with `@RestControllerAdvice`  

### Script to Speak:
"In production applications, we must never expose internal stack traces or messy errors to clients.

We created `GlobalExceptionHandler` using Spring's `@RestControllerAdvice`. It intercepts exceptions thrown anywhere in the application and transforms them into a uniform `ErrorResponse` JSON:
- If an order ID does not exist, it returns `404 Not Found`.
- If a client sends invalid data like an empty name or negative price, it returns `400 Bad Request` with an exact breakdown of which fields failed.
- If a client sends malformed JSON or passes letters instead of numbers in the URL, it returns `400 Bad Request`.
- And any unexpected error is safely caught and returned as `500 Internal Server Error`.

This ensures consistent, secure, and user-friendly communication with API clients."

## Slide 9: In-Memory Storage & Real-World Evolution
**Slide Title**: In-Memory Storage vs. Production Databases  

### Script to Speak:
"As requested, this project stores data in memory using Java's `ArrayList`. To make this thread-safe in a multi-threaded web environment, we marked our service methods as `synchronized`.

While in-memory storage is ideal for academic demonstration and rapid prototyping:
- Real-world production applications would connect to a persistent relational database like MySQL or PostgreSQL via Spring Data JPA.
- That would provide permanent data persistence, indexing for fast lookups, and ACID transactions.
- Because our project is built with a clean layered architecture, transitioning from our in-memory `OrderService` to a database repository requires changing only the data access layer without modifying our controller endpoints or API contract."
